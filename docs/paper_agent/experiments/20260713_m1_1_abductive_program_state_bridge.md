# M1.1 Abductive Program-State Bridge Experiment Brief

Timestamp: 2026-07-13 UTC

This is one of four independent candidate methods (`M1`--`M4`); no paper primary method has been selected. `M1-D0` remains a historical fixed-proxy kill and is not a result about M1.1.

M1.1's deployable sequence is fixed and maps directly to the implementation: (1) `extract_backward_obligations` derives suffix-required definitions and control requirements; (2) `select_v1_candidate` computes prefix/candidate forward facts plus parse, boundary, control, undefined-use, and contradiction diagnostics, using only candidate ordinal/text/canvas/seed; (3) `dependency_cone_plan` parses `prefix + candidate + suffix`, traces each suffix obligation to the latest candidate AST statement that defines it, recursively traces RHS def-use dependencies, and maps whole selected statement spans to candidate token indices; (4) M1 remasks that cone and runs a second `64` forwards; (5) equal-compute generic remask starts from the same selected state, uses the same initial remask cardinality, and also runs `64` forwards.

If a suffix-required definition or a recursive candidate dependency is absent, or an AST statement cannot be mapped back to token state, M1 records a concrete fallback reason. It switches to the fixed64 saved deployable state and executes a `64`-forward null refinement with no remasked tokens. It never creates a zero-forward copied row. Generic control uses the same fixed64 safe state in those cases, but continues its own 64-forward low-confidence refinement. Stage-one, generic, and dependency-cone raw outputs must use separate directories; each is resumable, deduplicated, and audited for missing, duplicate, and error keys.

Deployable selection/remasking may use only prefix, suffix, current candidate state, canvas, seed, AST/lexical syntax, and inference-visible confidence. It may not read reference code/canonical solution, unit-test or verifier outcome, passed label, oracle length, task ID, task group, row/source ID, split label, or frozen-test statistic. Evaluator test code is constructed only after selection and remask targets are fixed. Frozen controller test remains sealed with `test_evaluation_count=0`.

The run uses LLaDA-8B-Base, the existing evaluator, canvas `16/32/64/128`, seeds `0/1`, and `64` steps. A 12-case MultiLine technical smoke verifies protocol, schema, evaluator, seed/resume/dedup, missing/duplicate/error accounting, GPU memory, and actual second-stage forward counts; on technical pass it automatically proceeds to all `5079` non-frozen MultiLine spans without a performance gate. Reports include fixed64, ordinary-confidence best-of-grid, equal-compute generic remask, M1 score-only, M1 full, oracle ceiling, task-macro delta, descriptive span-micro accuracy, help/harm, buckets, forward/token budget, wall time, and memory. Promotion decisions, not full-run launch, may later use performance evidence.
